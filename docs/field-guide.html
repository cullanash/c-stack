cstack Field Guide

You do not write code. You say what you want and how to prove it is done. cstack makes Claude work like a careful engineering team: it reproduces, designs, builds, checks, and shows you the evidence.

—

The one rule

Every good cstack prompt has two parts. Give Claude a goal. Give Claude a way to check it. Claude picks the right playbook and the right skills. You do not name them.

The goal
What you want, in your own words.
The check
What you will see when it works.
/poteto-mode <what is wrong or what you want>. done means <what you will see>. show me the evidence.

A check is something that can pass or fail. "Make it better" is not a check. "The page shows <result> after I click <button>" is a check.

Default mode. cstack turns on poteto-mode by itself for real engineering work. Typing /poteto-mode at the start makes it certain. To turn it off for a session, say "no poteto-mode".
01

Set up once

Do these steps one time per computer, then one time per project.

  1. Install the plugin

    In Claude Code, add your cstack repo as a marketplace. Then install the plugin.

    /plugin marketplace add <owner>/cstack
    /plugin install cstack@cstack

  2. Start a new session

    The plugin loads its rules when a session starts. Close the current session. Open a new one in your project folder.

  3. Pick your models

    Run the setup skill. Answer its questions. The "balanced" budget is a good start.

    /setup-cstack

  4. Let Claude use a browser

    For a web app, Claude must click through the real app to prove a change works. Add the Playwright browser tool one time.

    claude mcp add playwright -- npx @playwright/mcp@latest

    Run this in your terminal, not in the Claude chat.

  5. Make a verification skill for your project

    This is the most important step. It teaches Claude how to start your app, use it like a user, and capture proof. Setup offers it at the end. You can also run it yourself.

    /create-verification-skill

    It writes .claude/skills/verify-<app>/ in your project. It proves itself one time before it hands over. If that proof fails, do not use it. Ask Claude to fix it.

  6. Keep the verification skill current

    Your app changes. The skill's feature map gets old. Run this after big changes, or once a week.

    /maintain-verification-skill

03

Features, bugs, new builds

What to type, what Claude does, and what you check.

understanddesignbuildverifycommitPR

What you type

/poteto-mode add <behavior>. <existing behavior> stays the same. done means <check>. verify it in the app and show me the evidence.

What Claude does (Feature playbook)

  1. Reads the code

    It runs /how on the part of the app you touch. It learns how it works now.

  2. Designs first

    It runs /architect. Several subagents sketch designs. Claude merges the best parts.

  3. Plans the work

    It writes what must happen first, what can run in parallel, and what must not overlap.

  4. Hands off the code

    A subagent writes the code with a clear scope and clear success criteria.

  5. Verifies

    It checks the real app, not the build log. "Inconclusive" is not a pass.

  6. Makes small commits and opens a PR

    It cleans the diff and writes a PR with a Verification section.

What you check

Read the Verification section. Look for the real result: a screenshot, a page state, a saved value. If you want to see the design before it builds, add "stop and show me the design first".

reproducefind causefixre-run reproPR

What you type

/poteto-mode <what happens> when <steps to trigger it>. it should <expected result>. repro first, then fix and verify.

"repro first" is a real rule, not politeness. Claude must make the bug happen before it changes code.

What Claude does (Bug fix playbook)

  1. Reproduces the bug

    It drives the app itself. It asks you only if it cannot reach the problem, and it tells you why.

  2. Finds the root cause

    It lists possible causes. It rules them out one at a time with runtime evidence. It uses /why if the bug is a regression.

  3. Plans the smallest fix

    Only the change the evidence supports ships. Extra "might help" code does not ship.

  4. Proves the fix

    The original repro now passes. If there is a cheap test, the failing test lands before the fix.

  5. Opens a PR

    The reply shows the failing output, then the passing output.

What you check

Look for two outputs: before (broken) and after (fixed). Look for a root cause in one or two sentences. If the reply says "added a check to prevent it" with no cause, say "fix root causes".

prototypeyou pickplan phasesbuildverify skillfeatures

Step A. Decide what to build with a prototype

/poteto-mode prototype <idea>. build 3 variants behind one switcher so i can compare. throwaway code. i will pick one.

The Prototype playbook builds throwaway versions in a scratch folder. It shows screenshots, tradeoffs, and a recommendation. The code is not for production. It exists only to help you decide.

Step B. Plan the real build in phases

/poteto-mode build <chosen direction>. it spans several phases. show me the phase plan and dependency order before you write code.

Large work routes to the Multi-phase plan playbook. If no playbook fits, Claude runs /figure-it-out to design a plan it can audit.

Step C. Make it provable

As soon as the app runs, run /create-verification-skill. From then on, each feature can be proven in the real app.

Step D. Add features one at a time

Use the Feature workflow for each piece. Five small PRs are better than one large PR.

Settle the data first. For a new build, the data shape decides most of the code. Say "use foundational thinking. settle the data model before any UI."
04

Check the reply

You do not review code. You review evidence.

Trust signals

  • The exact commands it ran, and their output.
  • Screenshots or page states from the real app.
  • Before and after results for a bug.
  • A step marked skip: <reason> instead of a silent skip.
  • "Inconclusive" when a check could not run.
  • The principles it applied, each with the decision it changed.

Red flags

  • "It builds" or "tests pass" as the only proof.
  • A confident "done" with no output.
  • A fix with no root cause.
  • Changes to files you did not expect.
  • The finish condition quietly changed.
  • A principle named with no decision behind it.

If a reply is too technical, type /bro. It restates the last message in plain words. For a deeper walk-through, type /teach me what this change does. convince me it fixes the cause.

06

Leave it running

An agent that proves its own work can work while you are away.

A safe handoff has four parts: the goal, a finish condition, permissions, and an exit.

/poteto-mode i'm stepping away. <goal> in a fresh worktree. done means <check that can pass or fail>. keep a decision log. don't ask me before committing. /loop until done. if you are stuck after a few hours, stop and write up why.
LineWhat it does
i'm stepping awayClaude stops asking and keeps going.
fresh worktreeThe run gets its own copy of the code. It cannot collide with your other work.
done means …Each loop checks this. The loop stops only when it passes.
decision log/show-me-your-work records each decision, reason, and evidence in a file.
don't ask me before committingGives permission in advance, so the run does not stop and wait.
/loop until doneClaude Code's loop command re-checks the finish condition.
stop and write up whyAn exit for a real dead end.

When you return, ask for the audit. Read its Attention section first.

/show-me-your-work catch me up on what you did.
A duration is not a finish condition. "Work on this for 4 hours" gives Claude nothing to check. You get 4 hours of activity, not a result.
07

Ship the work

Three separate steps. Each is its own decision.

StepSayWhat happensMerges?
Open the PR/poteto-mode open the pr. small ordered commits, evidence in the description.Cleans the diff. Writes a PR with Why, Scope, and Verification.No
Get it green/poteto-mode babysit this pr. get it green.Fixes conflicts, review comments, and failed checks. Stops at merge-ready.No
Land it/poteto-mode land the stack.A fresh agent verifies each PR. Then it merges the verified PRs in order.Yes

Only say "land" when you are ready for the change to go live. For a status check without action, say /poteto-mode check on pr <number>. anything outstanding?

Protect real data. Do not put real personal or health data in prompts, test data, or screenshots. Tell Claude to use synthetic test data for all verification.

09

Pitfalls

Do notDo this
List skills in order ("use /how, then /architect…").State the goal and the check. The playbook orders the skills.
Give a vague goal ("make it better").Give a check that can pass or fail.
Accept "it compiles" as done.Ask for the real result in the app.
Run two agents on the same code at once.Say "own worktree per task".
Accept every review comment.Read the Act on and Dismissed lists from /interrogate. Override when you disagree.
Keep one chat for many topics.Start with "new task", or open a new session.
Skip the verification skill.Make it first. Without it, Claude cannot prove UI changes.
Edit files in the cstack skills/ folder.Put changes in overrides/. The sync script replaces skills/.
10

Words to know

repro
Making a bug happen on purpose, so you can prove it is fixed later.
diff
The list of lines that a change adds and removes.
commit
A saved checkpoint of changes, with a message.
branch
A separate line of work. It does not affect the main code until it merges.
worktree
A second folder with its own copy of a branch. Agents use one each so they do not collide.
PR
Pull request. A proposal to merge a branch into the main code, with a description.
stack
A chain of small PRs. Each one builds on the one below it.
CI
Automatic checks that run on each PR.
merge
Adding the PR's changes to the main code. Usually this makes them go live.
subagent
A helper Claude that does one part of the work and reports back.
playbook
A fixed list of steps for one kind of task, such as Bug fix or Feature.
principle
A short named rule, such as "prove it works". You can say its name to steer Claude.
verification skill
Project instructions that teach Claude how to start and use your app to prove a change works.
